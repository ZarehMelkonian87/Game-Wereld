# Microfoon-diagnose per platform (T-52)

**Status:** diagnose-tooling klaar; wacht op metingen op echte toestellen (in te vullen door Zareh).
**Hoort bij:** `T-52` (diagnose) → `T-53` (oplossing) in [GDD-index §12.1](./GDD-index.md).
**Datum:** 2026-09-21

## 1. Aanleiding

Op desktop (Chrome/Edge, ook Safari op macOS) werkt de spraakherkenning in alle spraakmodi. Na de release op GitHub Pages werkt de microfoon op **telefoon en tablet niet** (release-test 2026-09-21, `DT-01`…`DT-03` op toestel eerder wél groen, maar dat was via `localhost`/dev-server op het thuisnetwerk). We weten nog niet _wáár_ het breekt: API afwezig, toestemming, of een sessie die start maar nooit iets teruggeeft. Zonder die meting is een oplossing (`T-53`) gokken.

## 2. Diagnose-tool in de app

**Waar:** Instellingen → kaart **"Microfoon-diagnose"** (ook bereikbaar als een geïnstalleerde app geen adresbalk heeft), of direct via `…/Game-Wereld/diagnose/microfoon`.

**Wat het scherm laat zien** (automatisch, zonder tikken):

| Regel             | Betekenis                                                                                                                                        |
| :---------------- | :----------------------------------------------------------------------------------------------------------------------------------------------- |
| Omgeving          | OS · browser · vorm (telefoon/tablet/desktop) · **browsertab of geïnstalleerde app** — hetzelfde signaal dat de download-gate gebruikt (`T-38`). |
| SpeechRecognition | of `SpeechRecognition`/`webkitSpeechRecognition` bestaat en de reden als niet (`api-missing`, `insecure-context`).                               |
| getUserMedia      | of de browser überhaupt om mic-toestemming kán vragen.                                                                                           |
| Mic-toestemming   | `granted` / `denied` / `prompt` / `unknown` uit de Permissions API (Safari heeft die niet → `unknown`, dat is normaal).                          |
| HTTPS / online    | GitHub Pages is https; "offline" betekent dat cloud-herkenning (Android) sowieso faalt.                                                          |
| Build             | bouwmoment van de geladen app — controleer dat dit ná de laatste release ligt (anders draait er nog een oude service-worker-versie).             |

**Vier stappen** (elke stap logt met tijdstempel in het rapport):

1. **Toestemming vragen** — `getUserMedia({ audio: true })`. Let op óf de browser een vraag toont. Resultaat `granted`/`denied`/`unsupported`.
2. **Korte herkenning** — één sessie, `continuous=false`, `interimResults=true`, `lang=nl-NL`. Zeg: _"zet de bal op het strand"_. Verwacht: `onstart` → `onresult` (tussentijds, definitief) → `onend`.
3. **Doorlopend luisteren** — exact de instellingen van Zeg & Zet (`continuous=true`, `latestSegmentOnly`, 4 s stiltestop, 25 s auto-stop). Zeg twee zinnen na elkaar.
4. **Eerst geluid, dan herkenning** — speelt een korte toon via een echte `<audio>` en start daarna meteen een korte herkenning. Test de iOS-hypothese dat de mic "hangt" nadat er media is afgespeeld.

**Watchdog:** komt er binnen 10 s géén enkele callback (`onstart`/`onresult`/`onerror`/`onend`), dan schrijft de tool `HANGT` in het rapport. Dat is het patroon van WebKit-bug 321436 (zie §4) en is anders niet te zien: de browser geeft dan geen fout.

**Rapport:** knop **Kopieer rapport** → plak in een bericht/notitie. Het rapport bevat omgeving, user-agent, API-status, toestemming en het logboek.

### 4a. Eerste toestelwaarneming (Galaxy A56, 2026-09-21) → hypothese H7

**Waarneming (Zareh, Samsung Galaxy A56, telefoon op Engels):** in Zeg & Zet gaat de mic aan, de wave beweegt mee met de stem en Android toont zijn eigen mic-icoon — maar er gebeurt niets, de zin moet opnieuw.

**H7 — de wave pakt de microfoon af (zeer waarschijnlijk de oorzaak op Android, mogelijk ook op iOS).** `MicWaveBars` opende tijdens het luisteren een **eigen `getUserMedia`-stream + `AudioContext`** om het echte volume te tonen (T-27). Op desktop kunnen WebRTC-opname en de spraakherkenner de mic delen; op Android (Chrome/Samsung Internet) en iOS niet: de herkenner krijgt stilte of geen buffer. Precies dit beeld: de wave (onze stream) reageert, het systeem-mic-icoon brandt (twee opnames), maar `onresult` blijft uit. Dit verklaart ook waarom `DT-01`…`DT-03` op desktop groen waren.

**Fix (1.56):** `MicWaveBars` is alleen nog audio-reactief op `formFactor === "desktop"`; op telefoon/tablet géén `getUserMedia`, wel een levendige "luister"-animatie (`data-audio-reactive="false"`). Unit tests bewijzen dat `getUserMedia` op phone/tablet niet wordt aangeroepen. **Te bevestigen op de A56** (`DT-11`): werkt Zeg & Zet nu met spraak? Zo ja, dan herhalen op iPhone — dezelfde conflict-bug (321436) beschrijft een niet-vrijgegeven audiosessie.

Over de telefoontaal (Engels): Chrome geeft onze `lang=nl-NL` door aan Google's herkenner; de systeemtaal hoeft niet Nederlands te zijn. Als het ná de wave-fix nog faalt, kijk in het diagnoserapport naar `onerror: language-not-supported`/`network` (stap 2/3).

### 4b. Rapport Galaxy A56 · Chrome 153 · geïnstalleerde app (2026-09-21) → H8

**Goed nieuws:** API aanwezig, toestemming `granted`, https, online — en de herkenner geeft Nederlandse zinnen terug (stap 3: _"… ik ga naar school zegt twee zinnen"_ 0,91; stap 4: _"Wij gaan naar school en jij gaat naar de"_ 0,92). H1/H2 spelen op Android dus niet; de mic kán.

**Twee Android-eigenaardigheden in het rapport, allebei bugs aan onze kant (H8):**

1. **Reeks lege resultaten bij het begin van spreken** — 7× "onnomatch" binnen één seconde (24.8–25.9 s). Dat zijn geen `nomatch`-events maar `onresult`-events zonder tekst; onze runtime vertaalde die naar `onNoMatch` → in het spel status **error** ("Ik kon de zin niet goed horen"), wave weg, terwijl de sessie doorliep. **Fix (1.57):** leeg `onresult` wordt genegeerd; alleen het echte `nomatch`-event telt.
2. **In continue modus (Zeg & Zet-instellingen) is élk tussenresultaat `isFinal=true` met zekerheid 0** ("blablablabla" → "… ik" → "… ik ga" allemaal _definitief_, zekerheid 0,80 = onze fallback voor 0); alleen het echte eindresultaat heeft zekerheid > 0 (0,91). Het spel verwerkte daardoor het eerste fragment ("zet") al als complete zin → "bijna"-feedback, en zo per woord. In niet-continue modus (stap 4) gedraagt Android zich wél netjes (tussentijds 0,00 → definitief 0,92). **Fix (1.57):** een "definitief" segment zonder zekerheid geldt als tussentijds (`isTrustedFinalSegment`); de zin wordt verwerkt bij het echte eindresultaat of, als dat uitblijft, na de 4 s-stiltetimer (status `heard`). Desktop-Chrome geeft eindresultaten altijd een zekerheid > 0 → ongewijzigd gedrag. **Let op bij het iPhone-rapport:** als Safari eindresultaten met zekerheid 0 geeft, valt Zeg & Zet daar terug op de stiltetimer (werkt, maar trager) — dan de regel per platform verfijnen.

**Nog open uit dit rapport:** stap 2 (eerste korte herkenning) gaf 6 s lang niets en toen `onend` — mogelijk nog niet gesproken; bij de tweede korte poging (stap 4) werkte het. Na de deploy van 1.56/1.57 opnieuw `DT-01` op de A56 doen.

**Prognose (vóór de meting):** meest waarschijnlijk een combinatie van **H1** (iOS geïnstalleerd: geen API) en **H3** (iOS Safari-tab: hangt na video/muziek) op Apple-toestellen, en **H4** op Android. Dan is `T-53` = **A2 + A5** (klein, snel) plus een keuze A1-of-B voor de geïnstalleerde iOS-app. Optie **C** (cloud-STT) blijft laatste redmiddel.

## 6. Wat er in de code al klaarstaat

- `src/app/screens/diagnose-microfoon/` — scherm + pure logica (`microphoneDiagnosis.ts`: browser/OS-detectie, rapportopbouw) met unit tests; route `diagnose/microfoon`; kaart in Instellingen (`MicrophoneDiagnosisLinkCard`).
- Bouwmoment als `__APP_BUILD_TIME__` (Vite `define`) — zichtbaar in het rapport.
- De tool hergebruikt exact dezelfde runtime-laag als het spel (`createBrowserSpeechRecognition`, `requestBrowserMicrophonePermission`), zodat een verschil tussen tool en spel zelf ook een aanwijzing is (zie H5).
